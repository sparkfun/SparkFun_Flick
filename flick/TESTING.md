# Testing

What has been tested on real hardware, what passed, and what is still open. Update this file after every hardware test.

Legend: ✅ passed · ❌ failed · ⚠️ passed with a note · 👀 needs a look by eye · ⬜ not tested yet · — does not apply to this board

## How to test a board

```
python flick.py baseline flash -t <target>     # once per Baseline change
python flick.py test                          # automatic checks, one PASS/FAIL table (~2 min)
python flick.py upload tools/tests/led_check     # LEDs, by eye: red, green, blue, white, off (1 s each)
```

- `flick test` runs `tools/tests/selftest` (memory, PSRAM, Strings, libm, time, Preferences, LittleFS, microSD, Ticker, the board's I2C devices, WiFi scan, BLE scan, WiFi connect + `WiFi.onEvent` + NTP + HTTP, then a 2 s deep sleep and the checks after waking), then a crash in `setup()` (`tools/tests/crash_test`, must roll back and be recorded in `INFO`), then a `loop()` that never returns (`tools/tests/hang_test`, the watchdog must catch it and roll back).
- WiFi checks need `WIFI_SSID`/`WIFI_PASSWORD` in `~/.flick/secrets.cfg` (`python flick.py wifi NAME PASSWORD`); without them they are skipped. On a chip without a radio (ESP32-P4) the WiFi and BLE checks are skipped.
- Before testing a new board, check it with `esptool flash-id`: the chip revision (classic ESP32: 3.0 or later) and the flash size against `flash_size` in its `target.json`.

## Issues found by testing

1. **BLE on the IoT RedBoard after WiFi (2026-10-22).** On the first `flick test` run, the BLE scan after a full WiFi session (connect, NTP, HTTP) crashed in setup three times in a row: `BLEDevice::init()` had failed (no PSRAM: little internal RAM left) and Baseline used the scan object anyway. **Fixed:** every BLE call now checks that the stack started and returns `BL_ERR_NO_MEM` otherwise, logging the largest free internal block. Three later runs passed without the failure. **Then at 2 Mbaud (same RAM, different luck) it failed differently:** `BLEDevice::init()` returned, but Bluedroid's own task crashed cleaning up after its start-up allocation failed (`l2c_free` in `BTU_StartUp`), out of Baseline's reach; and when it did start, a scan with ~40 devices around aborted on `operator new`. Measured: 132 KB free at sketch start, 62 KB with WiFi up, 9 KB after Bluedroid. **Fixed (2026-10-22)** by giving internal RAM back on the classic ESP32: the first BLE use releases Bluetooth Classic's controller memory when SPP has not started (SPP then reports a failure until restart; start SPP first to use both); BLE Mesh is compiled out (all chips); and on the boards without PSRAM (IoT RedBoard, Thing Plus C, DataLogger IoT) WiFi TX buffers are dynamic, 6 static RX buffers, and smaller BTC/BTU/timer task stacks (`targets/<t>/idf/sdkconfig.defaults`). Now 80 KB free with WiFi up and 20 KB after Bluedroid; `flick test` passes with the BLE scan after WiFi.
2. **Flash sizes in Arduino's board files are wrong for two boards:** the Thing Plus C6 and the IoT RedBoard both have 16 MB (Arduino says 4 MB). Their targets now use 16 MB. Always check with `esptool flash-id`.
3. **The IoT RedBoard's chip is rev 3.1**, not the ESP32-D0WDQ6 the hookup guide names, so Baseline's rev 3.0 requirement is met.
4. **Thing Plus C5: boot loop after the first flash (2026-10-22, recovered; watch for it).** The first time Baseline was flashed, the board reset every ~0.3 s with `rst:0x7 (TG0_WDT_HPSYS)` before printing anything, and esptool could no longer reset it into download mode. BOOT + RESET, then a plain RESET, cleared it, and the same Baseline then booted normally. Every later esptool flash leaves one watchdog reset (`INFO reset=7`) before a clean boot, and software restarts (`esp_restart`, after uploads) are clean. Best guess: the firmware the board shipped with left the flash or PSRAM interface in a state only a full reset clears. If a board loops after flashing, press RESET. The C5 also logs `MSPI Timing: Failed to allocate dummy cacheline for PSRAM memory barrier!` at start-up (an ESP-IDF message, PSRAM is initialized by Arduino after the heap); PSRAM tests pass regardless.
5. **Classic ESP32 console: tried 2 Mbaud, back to 921600 (2026-10-23).** 2 Mbaud worked on the IoT RedBoard's CH340, but uploads were no faster (bound by request/reply round trips: `selftest`, 15.8 KB, about 1 s either way), and about 3% of console replies lost a byte (2 of 60 `INFO` replies; 0 of 120 at 921600). That caused a failed `crash recorded` check once. `flick` still finds a board left at 2 Mbaud. The bootloader's own messages were at 115200 all along (IDF ignores the console baud setting unless the console UART is "custom").
6. **Pro Micro C3: too little heap for WiFi + BLE (2026-10-22, fixed).** The C3 has no PSRAM, and the code it keeps in IRAM comes out of the same 400 KB as the heap: 161 KB free at boot. **Fixed** by moving FreeRTOS, heap and Bluetooth-controller code to flash (`chips/esp32c3/idf/sdkconfig.defaults`): 205 KB free at boot.
7. **BLE scans grew without bound on NimBLE (S3, C3, C5, C6) (2026-10-22, fixed).** Baseline asked the BLE library for duplicate reports (right for Bluedroid on the classic ESP32). On NimBLE the library then appends every report to the device's payload, so each device's copy grew by kilobytes during a scan; on the C3 the heap ran out and the library aborted (`std::terminate`). **Fixed:** duplicates only on Bluedroid. The S3, C5 and C6 passed their BLE scans before the fix; re-run `flick test` on them to confirm.
8. **`flick test` missed console output once (IoT RedBoard, 2026-10-22).** One run captured only the after-sleep checks: the console was not read during the first phase right after the upload (likely the CH340 port briefly unavailable after `flick` closed it). **Fixed in `flick`:** it compares the PASS/FAIL lines it saw with the selftest's own `RESULT` count and runs the selftest again if lines are missing. **Also (2026-10-23):** lines the previous sketch printed during the upload (a selftest left running, its WiFi scan cut short) were counted as results (`FAIL WiFi scan`); `flick test` now ignores everything before the new selftest's `--- selftest` banner.
9. **DataLogger IoT: Qwiic and microSD are on a switched 3.3 V rail (2026-10-22, fixed).** With Baseline as first written, the Qwiic scan found only the on-board fuel gauge, and the card failed with `sdmmc_host_clock_update_command ... 0x107` (a stock Arduino sketch failed the same way). GPIO 32 enables the rail (high = on; `kDLBoardEn3v3_SW` in SparkFun's firmware, not in the hookup guide). **Fixed:** targets can define `BL_BOARD_EN_3V3_SW`, and Baseline drives it high at boot. Also from SparkFun's firmware: the RX/TX header is RX 16, TX 17 (the hookup guide lists them the other way round; not yet checked with a loopback). A3 (GPIO 39) added.

    - **Uploads above 115200 lost bytes**: the core turns the UART FIFO off (Mbed's driver dispatches only the FIFO-level interrupt, not the receive timeout), so every byte is an interrupt through Mbed's serial layer. Baseline now owns UART0's receive interrupt (FIFO on, level 1/8 plus receive timeout): 1300-character lines arrive intact at 921600; the 13.5 KB selftest uploads in 0.45 s. The BAUD reply must leave the transmit FIFO before the rate changes. flick and the web page now follow the rate Baseline names in its BAUD reply.
    - **Mbed's printf has no `%f`** (`MBED_MINIMAL_PRINTF` wraps the printf family): Baseline formats with newlib's `__real_vsnprintf` and links `_printf_float`.
    - Mbed calls `error()` (a reset) for a pin a peripheral can't use: Baseline checks pins against Mbed's pin maps first.
    - **The reset pin and DTR counted as crashes**: SVL, which runs first at every reset, ends with a software reset of its own, so an external reset reaches Baseline as one (RSTGEN STAT 0x10). A crash is now counted only on evidence: a `faulted` flag (SCRATCH1 bit 23) the fault handlers set, or the watchdog bit.
    - **The web page couldn't connect**: Web Serial raises DTR when it opens a port, which resets an Artemis; Baseline answers about 1.4 s later. `openLink()` now asks INFO again for up to 3.5 s on USB-serial boards and only accepts a reply with Baseline's fields (before, the page's sleeping-board catch sent SAFE and printed "Connected: undefined"). Uploads from the page stay at 115200 on an Artemis: a new rate means reopening, which resets the board.
    - **Serial1 defaulted to pads 0/1**, which aren't UART1 pads (0 has no UART; 1 is UART0): now TX1/RX1 as printed, pads 24/25 (the core's SERIAL1). `analogWrite()` now goes through Baseline's per-pin PWM: with the core's own `analogWrite()` the STAT LED (pad 5) stayed dark in `02_fade`; now it fades (seen 2026-11-19). A pad without a timer output switches on/off.
    - **Mbed's printf also ignores zero padding** (`%02x` prints `1`, `%08lx` prints `a0146`): plain `snprintf` in Baseline gives unpadded hex (INFO's `while(1) at 0xa0146`, crash lines). The BLE code formats addresses and UUIDs without printf.
    - **BLE (ArduinoBLE 2.1.0, `bl_apollo3_ble.cpp`).** Tested from the PC with bleak: `04_bluetooth/01_ble_serial` both ways 30/30 + 30/30 (lines of 20-165 bytes); `03_ble_server` read, write (no notification echoed back), notify (4-5 per 5.5 s at 1/s), 3 connect/disconnect rounds; `02_ble_scan` finds 7-25 devices with names; `flick test` 26/0/4 twice. GATT client not tested (no cooperative peripheral here). Found on the way: `BLE.begin()` takes about 3.1 s (2 s radio boot, 1 s lost to a late vendor-command completion that makes `HCI.reset()` time out); with the loader only in `bl_poll()`, an upload arriving meanwhile failed ("no reply during DATA", flick test step 3), so blocking library calls (start-up, connect, discovery, reads, writes) now run on a helper thread while the sketch's thread keeps polling the loader. BLE serial output sent one notification per byte (1-3 s per line); it is now buffered and coalesced (about 0.1 s). The controller's duplicate filter dropped scan responses (no names), so Baseline merges every report itself. RSSI reads about 40 dB higher than the PC's adapter for the same devices (left as the controller reports it). ArduinoBLE's own receive buffer is 256 bytes and drops what doesn't fit; Baseline takes the packets into 4 KB first.

31. **Internal RAM with Bluetooth Classic, BLE and WiFi (2026-11-20, RTK Postcard, COM116).** RTK Everywhere in SPP + BLE mode (Bluetooth Classic, two BLE serial services and a battery service) ran out of internal RAM on the classic ESP32: first a Bluedroid assert (`fixed_queue_new`, a semaphore it could not allocate), then RTK's `gnssRead` and `btRead` tasks were not created. Measured with heap prints at each step:
   - Bluetooth Classic SPP takes ~57 KB of internal RAM, each BLE serial service 7-14 KB, WiFi in station mode ~40 KB.
   - `heap_caps_get_largest_free_block(MALLOC_CAP_INTERNAL)` misleads on this chip: the largest block (20 KB) was IRAM, which holds no task stacks. Free 8-bit RAM was ~6 KB when the tasks failed.
   - Fixes (all classic ESP32 Baselines): Bluetooth BTC/BTU, esp_timer and timer service stacks from Arduino's 8 KB to 6/4.25/4/4 KB (+11 KB); 8 static WiFi TX buffers instead of 16 (frames beyond them wait in PSRAM); the part of the 32 KB sketch RAM window a sketch doesn't use goes to the heap (`ram_end` in the image header; RTK uses 20 KB, small sketches give back ~32 KB). `task_create` failures now log the stack asked for and the internal RAM left.
   - RTK's sketch stack was 16 KB in its sketch.cfg; its normal build uses Arduino's 8 KB loop task, so 8 KB there too.
   - Result: RTK starts SPP + BLE and all its tasks with ~9 KB of 8-bit internal RAM to spare; BLE tested from the PC (bleak): services, battery level, 10 KB of NMEA in 10 s. Not enough yet for WiFi on top (~40 KB).
   - Correction (issue 32): the static TX buffer count saved nothing. Arduino's WiFi starts with dynamic TX buffers and 4 static RX buffers unless a sketch calls `WiFi.useStaticBuffers(true)`.
32. **Bluetooth Classic, BLE, WiFi and TLS together (2026-11-20, RTK Postcard, COM116; ABI 1.10).** RTK Everywhere with SPP + BLE, then WiFi, an HTTPS request, and SPP and BLE connections from the PC. Each task's stack high-water mark and every internal heap block were read with a temporary heap walk in Baseline (`heap_caps_walk`; it keeps interrupts off long enough to lose upload bytes at 921600, so a chatty sketch goes to safe mode before an update). Where the internal RAM went, and what changed (classic ESP32 unless noted):
   - **Task stacks**, sized from their measured peaks, each keeping at least 1.4 KB unused: BTC 6 to 4 KB, esp_timer 4 to 3.5 KB (`CONFIG_TIMER_TASK_STACK_SIZE` is ESP-IDF's old name for it; the FreeRTOS timer service is `CONFIG_FREERTOS_TIMER_TASK_STACK_DEPTH`, now 2 KB), event loop 2 to 1.5 KB (ESP-IDF adds 2 KB), lwIP 4 to 3 KB, Arduino's `arduino_events` 4 to 3 KB (`idf/CMakeLists.txt`), Baseline's loader 6 to 4.5 KB (an upload peaks at 3.1 KB), stopwatch 3 to 2.5 KB, `bt_spp_tx` 3 to 2 KB. The `wifi` task's 6.5 KB is fixed in ESP-IDF's library.
   - **Bluetooth controller**: 1 BLE connection, 1 Bluetooth Classic connection, no SCO links: 5.7 KB. A BLE server accepts one central at a time.
   - **Console receive buffer** 8 KB to 5 KB (the UART driver keeps it internal; it holds the loader's window of 4 lines).
   - **BLE event queue** (16 x 256 bytes) in PSRAM, internal RAM without PSRAM (all chips).
   - **mDNS** allocates a block per packet and service, internal RAM only by default: RTK starts it when WiFi connects, and free RAM fell from 6.8 KB to under 300 bytes; an SPP connection then crashed Bluedroid (`fixed_queue_new`). Now its data goes to PSRAM first (`CONFIG_MDNS_MEMORY_CUSTOM_IMPL`, `mdns_mem_*` in `bl_impl_idf.cpp`, all chips) and its 4 KB task stack to PSRAM.
   - **Task stacks in PSRAM**: `CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM` (ESP-IDF leaves it off on the classic ESP32 for the PSRAM cache bug of revisions before 3, which Baseline doesn't support), and a new entry `task_create_caps` for sketches: `xTaskCreateWithCaps`, `xTaskCreatePinnedToCoreWithCaps`, `vTaskDeleteWithCaps`. Such a task must never write flash itself. `rtos_test` 23/23: a 16 KB PSRAM stack costs 588 bytes of internal RAM (the TCB), and its memory comes back when the task returns and when it is deleted.
   - **RTK** (its own repo): `gnssRead` and `handleGNSSData` (8 + 4 KB) run on PSRAM stacks (they write only the SD card, never flash), two BLE serial send queues of 4 packets instead of 10 (6.3 KB), the defaults built in place instead of a 4 KB static copy, and a 6 KB loop stack (peak 3.3 KB).
   - **Result:** 52 KB of internal RAM free after Bluetooth starts (10 KB before), 13.6 KB with WiFi connected and RTK's network services running, never below 9.9 KB through SPP and BLE connections. SPP 3/3 and BLE 2/2 with and without WiFi; HTTPS 9.8 KB. `flick test` 35/0/3, `net_test` 34/34, `idf_test` 26/26. An SPP connection takes 3.6 KB of internal RAM.
